# Template And Section Guidance

## Purpose

ATX Civil SMEs usually start from a feasibility template, but real studies diverge based
on jurisdiction, proposed use, site constraints, available evidence, customer questions,
and professional judgment.

The agent must understand the template as a starting structure, not a rigid form.

## Template Role

The template provides:

- Expected report organization.
- Standard section headings.
- Placeholder-driven data needs.
- House style for recommendations and caveats.
- Exhibit expectations.
- A default summary posture.

The template does not guarantee:

- Every section applies.
- Every section should receive equal detail.
- Section order is always sufficient for the client question.
- Placeholder values are available from BE.
- A default "appears feasible" conclusion is justified.

## Why SMEs Deviate

SMEs deviate from the template when:

- The site has a dominant feasibility blocker.
- The client asks a specific question.
- A jurisdiction has unique requirements.
- Public data is incomplete or contradictory.
- A report is focused on subdivision, solar, industrial, residential, or another
  specific use.
- Exhibits or surveys reveal constraints not captured by backend facts.
- Utility capacity, ROW/access, floodplain, OSSF, or easements drive the conclusion.
- The study needs to be shorter, longer, or organized around risk rather than template
  placeholders.

The agent should support deviations by explaining why a section is expanded, condensed,
merged, marked not applicable, or moved into the summary/risk register.

## Section Output Pattern

Every section draft should include:

1. Known facts.
2. Source citations.
3. Regulatory or engineering interpretation.
4. Data gaps or caveats.
5. Required or recommended actions.
6. Review status.

## Feasibility Posture

The summary should not default to "feasible" without support. Use one of these postures:

| Posture | Meaning |
| --- | --- |
| `feasible` | No material blockers identified with current evidence. |
| `feasible_with_conditions` | Feasible if listed studies, permits, extensions, or design changes occur. |
| `constrained` | Feasibility depends on significant unresolved constraints. |
| `infeasible_as_proposed` | Proposed program fails a known rule or practical constraint. |
| `insufficient_data` | Evidence is not sufficient to make a feasibility call. |

## Examples Of Legitimate Deviation

### OSSF-Driven Infeasibility

If public wastewater is unavailable and the parcel does not meet OSSF minimum lot size,
utility and summary sections should dominate the report. A normal template-length
zoning discussion is less important than clearly explaining the blocking condition.

### TxDOT Frontage

If the site fronts a state highway, ROW/access and transportation may need expanded
discussion even if the template treats them as ordinary sections.

### Edwards Aquifer

If the site is in the Edwards Recharge or Contributing Zone, watershed, water quality,
and permitting sections should be expanded and cross-referenced.

### Missing Survey Or Title

If easements, setbacks, or acreage are material but no current survey/title commitment
exists, the agent should not overstate buildable area. It should create document gaps
and recommend specific follow-up.

### Customer-Specific Questions

If the customer asks whether a specific development program is feasible, the report may
need a direct question-and-answer summary rather than only template section prose.

## Agent Behavior

The agent should:

- Start with the template section when applicable.
- Identify whether the section is complete, partial, ambiguous, not applicable, or
  insufficiently supported.
- Expand sections where project risk is concentrated.
- Condense or mark sections not applicable where justified.
- Preserve the professional ATX Civil voice.
- Explain deviations in trace/review metadata.
- Keep source support visible to the analyst.

The agent should not:

- Fill all placeholders just to complete a template.
- Hide missing information inside polished prose.
- Treat one jurisdiction's standard language as universal.
- Use generic feasibility language when a known blocker exists.
